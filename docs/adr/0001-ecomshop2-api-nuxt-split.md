# ecomshop2 splits the monolith into a Laravel API backend and a Nuxt frontend, keeping Filament and the layered architecture intact

`ecomshop` is a Laravel 12 + Livewire 3 monolith where storefront routes map directly to full-page Livewire components and there are no traditional controllers. `ecomshop2` replaces the storefront's presentation layer with a Nuxt frontend talking to a Laravel API backend, while keeping the Filament 4 admin panel, and the Migrations/Factories/Models/Repositories/Enums/Exceptions/Observers/Listeners/Mail/Exports layers, unchanged. The two apps live as `backend/` and `frontend/` inside one monorepo (`ecomshop2/`), built as a fresh Laravel install with the proven layers ported over deliberately — forcing every file to be re-examined for framework coupling — rather than stripping Livewire out of a copy of the existing repo in place.

Authorization uses **Sanctum SPA cookie-session auth**, not token/JWT auth, keeping the API and Filament on the same `web` session guard used today — no separate `api` guard is introduced. This is the least-migration-effort option from the current session-based setup and avoids the client-side token-storage/XSS tradeoffs of Bearer tokens; it requires the frontend and backend to share a top-level domain (`SANCTUM_STATEFUL_DOMAINS` / `SESSION_DOMAIN=.<domain>`), planned as `<domain>` → Nuxt, `api.<domain>` → Laravel + Filament.

API endpoints are **hybrid**: plain REST (`index`/`show`) for read-heavy resources (Products, Categories, Orders), and explicit verb-named action endpoints (`checkout`, `ship`, `deliver`, `cancel`, supplier actions) mirroring `OrderService`'s existing method shape, rather than forcing state transitions into generic CRUD verbs. `FormRequest` classes are kept for validation — Laravel already returns 422 JSON automatically for JSON-accepting requests, and the app already uses `FormRequest` as its validation convention (`CheckoutRequest`, `OrderSearchRequest`, `LoginRequest`, etc.), just not idiomatically: Livewire pages currently extract only `->rules()` from them (e.g. `LoginPage` calls `(new LoginRequest())->rules()`) because Livewire can't consume an injected, auto-validated `FormRequest`. In the API, these become real `FormRequest`s for the first time — `LoginRequest::authenticate()` and its rate-limiting already exist and go unused today. Laravel **API Resources** (`JsonResource`/`ResourceCollection`) become the new "view" layer replacing Blade/Livewire views, one per exposed model, controlling exactly what's serialized (e.g. hiding `supplier_id` from buyer-facing responses) without touching Services or Repositories.

Authorization checks move from Livewire's `boot()`/method-attribute pattern into Controllers, reusing the existing `Gate::define()` definitions unchanged (`abort_unless($orderService->canViewOrder($order, $user), 403)`, same as today) rather than introducing Policy classes — `OrderService` already owns the actual authorization logic, only the call site relocates. This retires `App\Attributes\PreAuthorize` and the `WithPreAuthorize` trait: that reflection-based shim exists only because Livewire actions bypass route middleware, which doesn't apply once real routes exist. `App\Attributes\Required` and its `ValidatesAttributes` trait (used by `UpdateProfileDto`) have no such coupling and port over unchanged. Domain exceptions (`OrderException`, `CartException`, `EmptyCartException`, `PaymentException`, `ProductNotFoundException`) stay framework-agnostic; the exception → HTTP status/JSON-shape mapping lives centrally in `bootstrap/app.php`'s `withExceptions()` callback as a single `match(get_class($e))`, rather than a `render()` method per exception class.

Deployment keeps the existing SSH + `git reset --hard origin/main` + `composer`/`artisan` pipeline for the backend (pointed at `backend/`), including `db:seed --force` on every deploy — confirmed safe because every seeder (`RoleSeeder`, `PaymentMethodSeeder`, the admin-user block in `DatabaseSeeder`) is already idempotent (`firstOrCreate`/`is_null` guards). The Nuxt frontend deploys through Hostinger's own Node.js hosting integration (git-webhook-triggered pull/build/restart, supporting SSR via `node .output/server/index.mjs`, Node 18–24) rather than through our own SSH/build steps — Hostinger's managed Node deploys don't support manual `npm` execution over SSH anyway. `deploy.yml` gets two path-filtered jobs (`backend/**`, `frontend/**`) in one workflow; the frontend job is a pre-merge quality gate only (lint + Vitest), with no deploy step, since Hostinger's webhook handles that independently once code lands on `main`.

Existing Pest tests that exercise Livewire components (`Livewire::test(...)`) are converted to HTTP-style Pest tests (`postJson`/`getJson`/`assertJson`) against the new API, exercising the same behaviors through the new transport.

Nuxt-internal decisions — SSR-vs-CSR per route, state management, UI kit, Vitest/Playwright setup — are explicitly deferred to a follow-up design session, since several (e.g. cookie forwarding under SSR) are downstream of the auth decision made here and would otherwise be guessed at.

## Considered options

- **Fork the existing `ecomshop` repo and strip Livewire out in place (rejected)** — preserves file history, but the current repo isn't even under git, and starting fresh forces every ported file to be verified as actually framework-agnostic rather than dragging along Livewire-specific config, service-provider wiring, and view-layer cruft that would otherwise go unnoticed.
- **Token-based auth (Sanctum personal access tokens) or JWT (chosen: rejected)** — needed only if the Nuxt frontend might be hosted on a domain outside our control, or if mobile clients are planned; otherwise it trades away session-based Gate checks that already work, in exchange for client-side token storage and its XSS surface, and (for JWT) self-managed refresh/rotation.
- **Introduce `Policy` classes replacing the ad-hoc `Gate::define()` calls (rejected)** — more idiomatic for a from-scratch Laravel API, but new abstraction for authorization logic that already lives correctly in `OrderService` and already works; rejected in favor of minimal-refactor continuity.
- **Per-exception `render()` methods instead of a central `withExceptions()` mapping (rejected)** — keeps each exception self-contained, but spreads the "how do errors become JSON" concern across five files instead of one, and reintroduces HTTP-response coupling into what are otherwise plain domain exceptions.
- **Have GitHub Actions build and SSH-deploy the Nuxt frontend itself, matching the backend job (rejected)** — would duplicate what Hostinger's managed Node.js hosting already does natively via its own git webhook, and Hostinger's managed deploys explicitly don't support the manual `npm`-over-SSH approach that would require.
